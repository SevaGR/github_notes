# Τι είναι το Github

Το Github είναι μια πλατφόρμα που κάνει host Git repositories. Μπορούμε να βάλουμε εκεί τα δικά μας repositories, να έχουμε access σε αυτά από οπουδήποτε και να τα μοιραστούμε με άλλους. Το Github προσφέρει επίσης διάφορα χαρακτηριστικά για συνεργασία με άλλους. Ουσιαστικά εξυπηρετεί στο διαμοιρασμό των repos και το collaboration σε αυτά.

# Βάζοντας τα αρχεία μας στο Github

#### Τι είναι το remote και πως το ορίζουμε

Προτού μπορέσουμε να κάνουμε push το οτιδήποτε στο Github, πρέπει να πούμε στο Git ότι υπάρχει το remote repository στο Github. Πρέπει να του δώσουμε (setup) έναν προορισμό (destination) στον οποίο θα κάνει το push. Στο Github αυτά τα destinations λέγονται remotes. Στην ουσία είναι ένα URL στο οποίο υπάρχει ένα hosted repository.

Για να ορίσουμε ένα remote κάνουμε χρήση της εντολής `git remote add <name> <url>`. Το name είναι ένα όνομα για το URL, λέει ουσιαστικά στο Git "αυτό το URL το λέω \<name>". Το name που δίνεται συνήθως είναι το `origin`.

#### Πως βλέπουμε τα remotes

Για να δούμε τα υπάρχοντα remotes για το repository μας, τρέχουμε την εντολή `git remote` ή `git remote -v` (verbose,). Αυτό εμφανίζει μια λίστα από remotes. Αν δεν έχουμε remotes, δε θα δούμε κάτι.

## 1η περίπτωση

Αν έχουμε ήδη ένα repository στον υπολογιστή μας και θέλουμε να το βάλουμε στο Github:
- Φτιάχνουμε ένα κενό repo στο Github
- Συνδέουμε το local repo (βάζοντας ένα remote)
- Κάνουμε push τις αλλαγές

## 2η περίπτωση

Αν δεν έχουμε ήδη κάποιο local repository μπορούμε:
- Να φτιάξουμε ένα καινούργιο repο στο Github
- Να το κάνουμε clone στον υπολογιστή μας (σε ένα κενό git repo)
- Να κάνουμε ότι αλλαγές θέλουμε
- Και τέλος να κάνουμε push τις αλλαγές


# Push

Αφού έχου ορίσει ένα remote μπορούμε πλέον να κάνουμε `push` τις αλλαγές μας στο Github. Με την εντολή `git push <remote> <branch>`, "στέλνουμε" το συγκεκριμένο branch που θα ορίσουμε στο Github repository μας (στο remote). Αν είναι το πρώτο commit push σε αυτό το Github repository, θα δημιουργηθεί ένα καινούργιο branch στο Github. Γενικά το Github δε σχετίζεται άμεσα με το Git repository στον υπολογιστή μας! Είναι διαφορετικό το local branch (local git repo) με το remote branch (Github) Αν ξανακάνουμε push, θα ενημερωθεί το branch στο Github με τις αλλαγές που κάναμε. 

Μπορούμε να κάνουμε `push` ένα συγκεκριμένο local branch σε ένα συγκεκριμένο remote branch με την εντολή `git push <remote> <local-branch:remote-branch>`. Λέμε στην ουσία "στείλε το local branch στο συγκεκριμένο remote branch του remote". 

## The -u option

Μπορούμε να φτιάξουμε ένα "connection" (set an upstream) μεταξύ του local branch και του remote στο Github. Αυτό γίνεται με την εντολή `git push -u origin master` και μας επιτρέπει να κάνουμε πιο εύκολα το `push` με μια απλή `git push`. Με το `-u` option λέμε ουσιαστικά στο Git να "θυμάται" ότι το συγκεκριμένο local branch είναι συνδεδμένο με το remote branch και όταν κάνουμε push, το συγκεκριμένο local branch θα καταλήγει στο συγκεκριμένο remote branch.


# Remote Tracking Branches

Όταν κάνουμε clone ένα repository από το Github, καταλήγουμε με ένα local repository όπως το ξέρουμε. Κατά τα γνωστά, στο τελευταίο commit του branch (έστω master branch) υπάρχει ο γνωστός δείκτης master. Υπάρχει όμως και ένας δείκτης origin/master (για την ακρίβεια είναι τύπου \<remote>/\<name>) που δείχνει στο τελευταίο commit, στο (master) branch στο origin (στο remote repository). Αυτός ο δείκτης λέγεται Remote Tracking Branch και δε γίνεται να μετακινηθεί από εμας. Για να δούμε τα Remote Tracking Branches, χρησιμοποιούμε την εντολή `git branch -r`.

Με το δείκτη αυτό έχουμε τη δυνατότητα να κάνουμε χρήσης της εντολής `git checkout <remote>/<name>` (ανάλογα τι ονόματα έχουν), και να μπούμε σε detached HEAD mode για να δούμε σε τι κατάσταση είναι το branch σε εκείνο το σημείο. Αν κάνουμε push, ο δείκτης αυτός θα προχωρήσει. 

Όταν κάνουμε clone ένα Github repository με πολλά branches, ενώ τα remote tracking branches φαίνονται με την εντολή `git branch -r`, τα branches αυτά δε "φαίνονται" στα local αρχεία μας, υπάρχει μόνο το origin/main. Ακόμα, το master branch μας στα local αρχεία μας θα είναι αυτόματα linked με το origin/main.

Με την εντολή `git switch <remote-branch-name>` (βάζοντας το ίδιο όνομα με το remote branch που θέλουμε να γίνει το connection), φτιάχνουμε ένα νέο local branch από το remote branch και ταυτόχρονα κάνει και το connection μεταξύ των δύο. Έτσι αποκτάμε πρόσβαση στο συγκεκριμένο branch. Μπορούμε ωστόσο αν θέλουμε, αν και δε συνηθίζεται, να φτιάξουμε και να συνδέσουμε 2 branches με διαφορετικό όνομα.


# Fetch

Ας υποθέσουμε ότι έχουμε κάνει clone ένα repository και δουλεύουμε σε κάποιες αλλαγές σε ένα branch. Όσο εμείς δουλεύουμε σε αυτό και κάνουμε commits, υπάρχει περίπτωση κάποιος άλλος να έχει κάνει τα δικά του commits στο ίδιο branch. Κάνοντας fetching, κατεβάζουμε τις αλλαγές αυτές από το remote repository ΑΛΛΑ αυτές οι αλλαγές δε θα ενσωματωθούν αυτόματα στα δικά μας αρχεία (working files). Μας επιτρέπει να δούμε σε τι εργάζονται οι άλλοι, χωρίς να κάνουμε merge τις αλλαγές στο δικό μας local repo.

Αυτό το κάνουμε με την εντολή `git fetch <remote>` δίνοντας το remote που θέλουμε να κάνουμε fetch (ενδεχομένως να έχουμε περισσότερα από ένα). Αυτό κάνει fetch τα branches και το history από το συγκεκριμένο remote repository. Κάνει update μόνο τα remote tracking branches. Μπορούμε να κάνουμε fetch ένα συγκέκριμένο branch με την εντολή `git fetch <remote> <branch>`. Αν δεν καθορίσουμε το remote και γράψουμε `git fetch` τότε by default γίνεται fetch του origin.

Κάνοντας `git status` ή `git log` στο local repository, δε θα δούμε να έχει αλλάξει κάτι. Για να δούμε αυτές τις αλλαγές κάνουμε χρήση του remote tracking branch με την εντολή `git checkout <remote>/<branch-name>` (που μας βάζει σε detached HEAD state).

# Pull

Το `git pull` είναι μία ακόμα εντολή που μας επιτρέπει να πάρουμε τις αλλαγές που έχουν γίνει σε ένα repository. Η διαφορά με το fetch είναι ότι το pull κάνει ταυτόχρονα και update το HEAD με όλες τις αλλαγές που έχουν γίνει στο remote repository.  Είναι σαν να κάνουμε `git fetch` (update remote tracking branch με τις τελευταίες αλλαγές) και έπειτα `git merge` (update current branch με τις αλλαγές που έχει το remote tracking branch).

Έχει σημασία απο ΠΟΥ θα τρέξουμε την εντολή (όπως και στο `git merge`) καθώς εκεί που θα την τρέξουμε θα γίνουν και οι αλλαγές. Όπως και με τη `git merge` υπάρχει πιθανότητα να υπάρξουν conflicts. Μπορεί για παράδειγμα να υπάρχει ένα αρχείο στο οποίο έχουμε κάνει αλλαγές για τις οποίες το Github δε γνωρίζει και αντίστοιχα κάποιος άλλος να έχει κάνει αλλαγές στο ίδιο αρχείο για τις οποίες το local repository μας δε γνωρίζει. Όταν κάνουμε `git pull` θα προκύψουν conflicts που θα πρέπει να επιλυθουν. Αφού γίνει αυτό, το local repository μας θα είναι κάποια commits πιο μπροστά από το remote, αφού θα έχει πλέον τις αλλαγές του remote αλλά θα έχει και τις αλλαγές τις οποίες δε γνωρίζει ακόμα το Github. Εκεί λοιπόν αν θέλουμε να περαστούν οι αλλαγές στο remote, κάνουμε `git push`.

Αν δεν ορίσουμε το \<branch> καλόντας την `git pull`, τότε το \<remote> θα είναι by default το origin και το \<branch> θα είναι οτιδήποτε έχει οριστεί σαν tracking connection για αυτό το branch (εξηθήκε πιο πάνω με την `git switch` στα Remote Tracking Branches). Αυτή η συμπεριφορά μπορεί να τροποποιηθεί και τα tracking connections μπορούν να αλλαχτούν από μεσά. Αυτό κάνει πιο εύκολη τη διαδικασία του `git pull`.

# Public vs Private Repos

Τα public repositories, όπως λέει και το όνομα, είναι διαθέσιμα σε όλους. Οποιοσδήποτε μπορεί να τα δει και να τα κάνει clone. Δε μπορούν να τα τροποποιήσουν άλλοι εκτός και τους έχει δωθεί η άδεια.

Τα private repositories δε φαίνονται σε κανέναν άλλο εκτός από αυτόν που τα έφτιαξε και στους collaborators.

# READMEs

Είναι ένα markdown αρχείο (κατάληξη .md) στο οποίο εξηγούμε τι ακριβώς κάνει το project μας, πάνω σε τι δουλεύουμε, για ποιον είναι, πώς να το τρέξει κανείς, ποιός συντηρεί το project κλπ.

# Pull Requests

Τα pull requests είναι ένα χαρακτηριστικό του Github και όχι του Git. Μας επιτρέπουν να ειδοποιούμε τους υπόλοιπους στην ομάδα ότι υπάρχει κάτι καινούργιο (π.χ. ένα καινούργιο χαρακτηριστικό) το οποίο πρέπει να κάνουμε review. Μπορούμε έτσι να το εξετάσουμε, να το αποδεχτούμε ή να το απορρίψουμε προτού γίνει το οποιοδήποτε merge.

Η λογική είναι ότι:
- το main branch θα είναι protected και δε θα μπορούμε να κάνουμε αυθαίρετα merge
- δουλεύουμε σε ένα δικό μας branch locally και αφού τελειώσουμε
- κάνουμε ένα pull request με το branch που φτιάξαμε και
- περιμένουμε είτε να γίνει αποδεκτό, όπου θα γίνει merge, είτε να απποριφθεί

# Forking

Σε projects που δεν είναι δικά μας και δεν είμαστε collaborators, μπορούμε να φτιάξουμε ένα fork. Αυτό δημιουργεί ένα νέο Github repository στο λογαριασμό μας και είναι ουσιαστικά ένα κανονικό αντίγραφο του πρωτοτύπου. Και αυτό το χαρακτηριστικό είναι του Github και όχι του Git.

Σε αυτό το forked repository, μπορούμε να κάνουμε οτιδήποτε θέλουμε και έπειτα μπορούμε να κάνουμε pull request στον κάτοχο του πρωτοτύπου. 

Σε μία τέτοια περίπτωση θα θέλουμε τη δυνατότητα να μπορούμε να κάνουμε pull τις αλλαγές που θα γίνονται στο πρωτότυπο. Για να το κάνουμε αυτό, πρέπει να στήσουμε ένα remote που θα αναφέρεται στο πρωτότυπο οπότε χρησιμοποιούμε την εντολή `git remote add <remote-name> <URL>`. Συνηθισμένα ονόματα για το remote σε περιπτώσεις που έχουμε ένα fork είναι το upstream ή το original.

# Rebasing

Πολύ χρήσιμο αρκει να ξέρουμε πότε να ΜΗΝ το χρησιμοποιούμε. Χρησιμοποιείται είτε σαν εναλλακτική για το merging είτε για να καθαρίσει το commit history.

Αν για παράδειγμα σε ένα μεγάλο project χρειάζεται να κάνουμε συχνά merge το main branch στο feature branch μας στο οποίο δουλεύουμε, αυτα τα merges θα περιέχουν "άχρηστα" commits για το δικό μας branch. Εδώ έρχεται το rebase το οποίο ξαναγράφει το ιστορικό των commits, βάζοντας το merging branch (στο παράδειγμα το main) στην αρχή και το feature branch το βάζει να ξεκινάει(!) εκεί που τελειώνει το main (στο HEAD του). Δεν έχει αλλάξει κάτι στα branch, όλο το history είναι εκεί απλά το ξαναγράψαμε (rewrite history). Το rebase φτιάχνει commits για κάθε ένα από τα original feature branch commits.

Η εντολή που χρησιμοποιούμε είναι η `git rebase <branch>`. Όπως και με τη `merge`, πάμε πρώτα στο branch που θέλουμε να κάνουμε το rebase (στο παράδειγμα στο feature branch) και κάνουμε rebase με το branch που θέλουμε να γίνει το rebase (στο παράδειγμα το main). Οπότε πρώτα κάνουμε `git switch feature` και έπειτα `git rebase main`. 

 Στο παραπάνω παράδειγμα το χρησιμοποιούμε για να καθαρίσουμε το commit history ενώ έχουν γίνει κάποια merges, όμως μπορεί να χρησιμοποιηθεί και αντί του merge και θα έχουμε το ίδιο αποτέλεσμα.

### Γιατί να κάνουμε rebase;

Μας δίνει ένα πιο καθαρό commit history και είναι πιο εύκολο να καταλάβει κανείς τι έκανε ο καθένας στο project, φαίνονται πιο καθαρά τα commits και από ποιον έγιναν. Προτιμάται για παράδειγμα στα open source projects που γίνονται πολλά commits ταυτόχρονα

### Πότε να ΜΗΝ κάνουμε rebase - Ο χρυσός κανόνας

Δεν κάνουμε ΠΟΤΕ rebase αν έχουμε κάνει share τα commits μας με άλλους. Αν δηλαδή έχουμε κάνει push τα commits στο Github, ΔΕΝ κάνουμε rebase εκτός και είμαστε απόλυτα σίγουρα οτι κανένας από την ομάδα δε χρησιμοποιεί αυτά τα commits. Συνεπώς αν τα έχουμε μοιραστεί ΔΕ θέλουμε να ξαναγράψουμε το git history που έχουν ήδη άλλοι χρήστες. Είναι πολύ δύσκολο να χειριστούμε τη μετέπειτα κατάσταση. Για παράδειγμα ΔΕΝ κάνουμε rebase το main branch. Το κάνουμε πχ στο feature branch μας για να πάρουμε αλλαγές από το main. Αλλά όταν κάνουμε push το feature branch μας, δεν ξανακάνουμε rebase σε αυτό γιατί πλέον το έχουν και οι υπόλοιποι.
